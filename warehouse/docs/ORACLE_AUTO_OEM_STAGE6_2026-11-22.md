# CarPot — автоматичний OEM із Oracle (Warehouse staging, Stage 6)

**Статус:** реалізація в ізольованій feature-гілці, застосування до Railway вимагає окремого deployment. Не є підтвердженням 90% покриття OEM.

## Призначення

Продавець додає автомобіль і працює з наявними картками; жодних кнопок «Завантажити OEM», окремих покупок або технічних OEM-сповіщень. Фоновий Warehouse OEM worker автоматично підбирає OEM із локального/компактного каталогу та з read-only Oracle Gateway.

Потік: Warehouse staging → авторизований Catalogue staging HTTPS → приватний Relay/Tailscale → Oracle Adapter (SELECT-only MySQL).

## Активування (тільки Warehouse staging)

Сервіс Warehouse API у Railway: `telegram-bot` (середовище `warehouse-staging`). Задати **`WAREHOUSE_ORACLE_OEM_ENABLED=true`** та застосувати feature-гілку тільки до цього сервісу. Без цієї змінної поведінка залишається попередньою.

- `WAREHOUSE_CATALOGUE_URL`, `WAREHOUSE_CATALOGUE_HOST` і `WAREHOUSE_CATALOGUE_KEY` — уже існуючий авторизований HTTPS-клієнт Catalogue.
- `WAREHOUSE_AUTO_OEM_ENABLED` — уже чинний фоновий lifecycle; стандартно ON у staging, OFF поза staging.
- **Заборона:** Oracle-виклики з автоматичного OEM механізму неможливі, якщо середовище не staging, незалежно від прапорця.
- Операційне вимкнення: встановити `WAREHOUSE_ORACLE_OEM_ENABLED=false` у staging й передеплоїти Warehouse API. При цьому вже вибрані/збережені OEM не видаляються автоматично.

## Правила доказовості

1. Oracle відповідає на запит тільки за **точною трійкою** `manufacturer_id + supplier_id + article_number`; метод перевіряє підпис API, очікувані ID, всі поля та неповноту (`truncated`). Усі неповні/невірні відповіді відхиляються.
2. Для плану деталей потрібне існуюче **джерельне зв'язування** PRD із конкретною модифікацією автомобіля (`article_batch` / `saved_articles`). Доповнюємо тільки відсутні OEM у цих джерельних артикулів, НЕ з інших модифікацій.
3. Для складської картки з точним артикулом/брендом і наявним перевірюваним `supplier_id` можлива окрема OEM-кросреференція; ID виробника автомобіля тільки з прив'язаної модифікації або перевіреної існуючої exact-article відповіді.
4. `vin_verified=false` залишається незмінним. **OEM-кросреференція ≠ перевірена застосовність (fitment)**. Не заявляти VIN-сумісність без завершеного graph `article_links` і прив'язки модифікацій.
5. Наявні ручні OEM, ручне очищення, продані позиції та історичні операції захищені поточною логікою `fill_part/refresh_stock_reference/fill_exact`. Не змінюємо облік залишків чи цін.

## Обмеження навантаження та повторне використання

- Максимум **24** нових перевірок на один прохід збагачення донора.
- Ротація курсора по позиціях запобігає постійному залипанню на перших деталях.
- Кеш успішних відповідей, у т.ч. порожніх (лише в межах роботи поточного worker).
- Максимум 2 upstream failures за прохід; недоступність Oracle не блокує складські операції.
- Фоновий sweep уже існує, інтервал 120 секунд між повними проходами; це не синхронна операція натискання користувача.

## Подальша фаза

Після завершення імпорту `article_li`/`article_links`: перевірити повноту source graph, додати доказові OEM → PRD → модифікація → VIN зв'язки, заміряти покриття для DAF XF / Volvo XC90 / Volvo XC60. Ціль ≥90% може бути підтверджена **лише фактичним аудитом** і за достатньої повноти джерела. Не запускати масовий імпорт, DDL або платні VIN API в цьому етапі.
