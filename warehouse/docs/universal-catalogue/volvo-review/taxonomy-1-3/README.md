## Використання і безпека

- `catalogue_import.py`, `plan_parts_classification.py`, API `catalogue.py` — advisory-пропозиції; не міграція історичних позицій.
- `universal_catalogue.ReviewedType` та `unified_catalogue.validate_plan` — валідація тих самих корпоративних шляхів.
- `source_types.Resolver(provision=True)` може додавати відсутні категорії лише при виклику чинного provisioning. Існуючі ID залежать від account/root/назви, не від загальної кількості підкатегорій; старі назви не змінені. Цей шлях не викликали на staging.
- `assemblies.tree` повертає category/subcategory; `AssemblyTree.tsx` уже виводить breadcrumb динамічно. Нові frontend-списки або дублікати таксономії не додавали.
- Source ID, source context checksum, canonical candidate ID та попередні review-пропозиції всіх 113 збережено; owner approval лишається PENDING_OWNER_REVIEW.
- Чинний `prepare()` двічі обробив 113 реальних source records з ідентичним результатом: 113 review / 0 фізичних типів без схваленого review / 0 production/staging writes.
- Не було автоматичного перепризначення складських категорій, створення Part/AssemblyMembership, зміни продажів, резервів чи історії. DB-тести виконуються тільки на localhost:55441 у dedicated `_test` БД.
