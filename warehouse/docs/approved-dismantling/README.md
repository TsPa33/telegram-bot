# Затверджений інтерфейс розбору

Один користувацький робочий екран для збереженого Plan.Parts-плану: прогрес, модифікація, категорії, компактний список, групові дії та керування українськими назвами. OEM стоїть перед артикулом; варіанти артикулів розгортаються безпосередньо під рядком. Демонстраційні числа макета не використовуються як дані.

## Збереження й безпека

- GET не створює позицій або надходжень. Показники рахують записи плану; кількість одиниць та кількість пропозицій не підміняють кількість позицій.
- Оприбуткованою вважається позиція з історією надходження або позитивним залишком і явним розміщенням на полиці. Віртуальна кількість на автомобілі сама по собі не є надходженням.
- Назви: ручне уточнення → перевірений словник → збережений переклад DeepL → оригінал. Оригінал доступний для пошуку. Переклади зберігаються в PostgreSQL окремо для workspace, до 40 ключів за пакет; advisory lock координує паралельні запити. Автоматичний переклад запускається після явного формування/відновлення списку, не при відкритті збереженого плану. Збій між зовнішньою відповіддю DeepL і commit може потребувати повторного запиту; exactly-once billing не гарантується.
- Приховування, повернення, демонтаж і назва — рішення плану; вони не переписують залишки, ціни, фінанси та історичні надходження. Старі складські виключення не скасовуються приховано.
- Артикули спершу читаються через наявне безплатне recovery. Новий платний запит потребує чинної серверної вартості та підтвердження. Жодного реального платного запиту під час перевірок.
- Призначення номера використовує наявну серверну перевірку workspace/донора/K-Type/типу/складської картки/art_id. Для неоднозначної картки потрібен явний вибір. Без точної прив'язки базового типу Plan.Parts не вгадується.
- OEM вводиться окремо вручну; автоматичний OEM endpoint не вигаданий і не активований. OEM-крос не є підтвердженням VIN-сумісності.
- Складська дія має окреме підтвердження. Для існуючої позиції переміщення на полицю не змінює кількість чи ціну; нова фізична одиниця додається тільки явною дією.

## Міграція

Єдина head `c4197e2a8d60`, parent `bd18a9f37c20`. Лише дві нові таблиці: `dismantling_annotations` та `part_name_translations`; без backfill або зміни старих таблиць. На окремій заповненій локальній PostgreSQL upgrade виконано двічі: хеші даних усіх 53 попередніх таблиць незмінні. Автоматичний downgrade із видаленням користувацьких рішень заборонений. Застосування — штатний startup API, не ручна повторна міграція.

## Перевірки

- Backend: 7 PASS (новий read model/переклад/ізоляція/CSRF/рішення + початковий сценарій).
- UI unit: 14 PASS, включно з точною відповідністю перевіреного словника.
- Frontend production build: PASS; попередження про розмір bundle залишається.
- Browser: локальний production build + справжня disposable PostgreSQL, 1440px і 390px. Призначення артикула, OEM, ручна назва, reload, міжсторінковий вибір, приховування/повернення/демонтаж, явна складська дія, новий базовий список без удаваних надходжень. Немає JS errors, горизонтального overflow, платних lookup-запитів. Plan.Parts і DeepL — контрольовані mocks, не live-відповіді.

Основні файли: `DismantlingBoard.tsx`, `dismantling-board.css`, контролери `VirtualDismantling.tsx` / `PlanPartsDonorAnalysis.tsx`; backend `api/dismantling_workspace.py`, `services/dismantling_workspace.py`, `models/dismantling_ui.py`, міграція, спільний перевірений словник та цільові тести.

Скриншоти й результати поруч. Це локальне приймання, не підтвердження staging deployment. Railway недоступний у поточній сесії; ізоляцію staging раніше явно підтвердив власник. Після push необхідно окремо підтвердити Auto Deploy, startup migration та авторизований staging UI. Production, Variables і live Plan.Parts не змінювалися.

## Попередній блокер публікації (усунуто інтеграцією)

Fetch під час завершення виявив remote `a7b6eee680c6e3e7f642ef9311cfb841610ac95a`, 8 нових комітів після локальної бази `69f316c933d44479b95b573893a59d75d0225b08`. Remote замінив `VirtualDismantling.tsx` на professional-only entrypoint і змінив `PlanPartsDonorAnalysis.tsx` та підтвердження вартості. Поточна реалізація протестована на локальній базі, а не на цьому новому remote. Push не виконувався: потрібне узгодження інтеграції зі збереженням нових remote-рішень. Force-push, автоматичний rebase/merge, deployment або зміни staging-даних не виконувалися.


## Інтеграція актуальної feature-гілки

Об'єднано локальний `ed1399ffb6033e19b62bb1b36368bc5b6ad0a6fb` і remote `a7b6eee680c6e3e7f642ef9311cfb841610ac95a` через merge без переписування історії.

- Конфлікт `VirtualDismantling.tsx`: збережено professional-only entrypoint remote. Базовий тестовий каталог у UI не повертається; backend-сумісність з історичними планами збережена.
- Конфлікт `PlanPartsDonorAnalysis.tsx`: remote-керування модифікацією, явне підтвердження вартості й recovery поєднані з локальною DismantlingBoard. Старі великі таблиця/менеджер не відображаються паралельно.
- Автопереклад запускається лише після явного отримання/відновлення списку; читання збереженого плану його не запускає. Ручні назви, прогрес, OEM та inline-призначення збережені.
- Повторено тільки frontend build, 14 цільових unit-тестів і браузерний сценарій конфліктних компонентів. Стандартний prebuild також запускає свої наявні перевірки. Backend і міграція під час merge не змінювалися; попередні докази їх перевірок залишаються чинними.
- Актуальне browser-приймання: 1440/390px, категорії/пагінація/вибір, збережене призначення номера й виробника, OEM, ручна назва, приховування/повернення/демонтаж, reload; новий автомобіль має Plan.Parts-початок і підтвердження перед пошуком модифікації, без базового каталогу. Провайдери — локальні mocks, реальні платні API не викликалися.
- Railway connector/CLI відсутні. Автоматичне staging deployment та міграція на staging потребують окремої перевірки через підключений Railway; це не локальне підтвердження розгортання. Production та Railway Variables не змінювалися.
