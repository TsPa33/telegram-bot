# Стабілізація каталогу, розбору та складу

База реалізації: `993c5224d84e5522874e0b655134f286a41f6ac0`. Зміни тільки у Warehouse. Production, Railway Variables, зовнішні платні API та дані staging не змінювалися під час локальної перевірки.

## Що виправлено

1. **Категорії.** Один backend Resolver використовує точний `plan.parts + pt_id`, перевірену оригінальну назву й чинну корпоративну таксономію. Нове постійне зіставлення зберігає CarPot type key (незалежний від моделі автомобіля), категорію, підкатегорію, рішення та історію попередніх рішень. Переклад не є ключем ідентичності. Зміна значення vendor type потребує уточнення. Для невизначеного типу нова категорія не вигадується.
2. **Безпечне виправлення старих даних.** Наявні classification preview/apply endpoint повторно використані, без паралельного механізму. Preview повертає старі/нові відповідності й SHA-256 token. Apply відхиляє застарілий preview, змінює лише однозначні порожні категорії та додає аудит. Усі вже призначені категорії захищені: через відсутність надійної історичної ознаки ручного призначення їх не можна безпечно автоматично перезаписувати. Ідентичність Part, quantity/reserved, selling_price/currency, OEM/артикули, історичні operations не переписуються.
3. **Корпоративні корені.** Імпорт/додавання деталей не створює кореневих категорій. Відсутні 12 корпоративних коренів та затверджені підкатегорії готуються тільки окремою явною дією власника після preview. Архівні корпоративні вузли не відновлюються приховано. Неоднозначні однакові корені не вибираються довільно. Частини дерева зі старими назвами залишаються в БД.
4. **Фільтри складу й пошуку.** Корпоративні root aliases групуються в одні й ті самі 12 категорій, підкатегорії доступні після вибору кореня. Конкретні назви деталей, підкатегорії та службові source/ID не є верхніми опціями. «Потребує уточнення» знаходить також некатегоризовані та старі неузгоджені корені. Frontend aliases згенеровані з backend-словника; тест перевіряє точну відповідність.
5. **Batch.** Одноразові перевірки прав, донора та дозволених типів; один запит на наявні картки; попередньо завантажена таксономія/мапи; bulk flush нових Part; наявні `stock()` і `record()` з відкладеним flush; один commit. Помилка відкочує весь пакет. Пакет — до 1000 типів, один HTTP і одна транзакція, без прихованих часткових commit між чанками. Прогрес показує початок і фактичне завершення, без штучних відсотків. Нові позиції отримують 1 шт.; існуючі, включно з нульовими/архівними, повторно не оприбутковуються. Різні `pt_id` не зливаються через однаковий переклад. `receive-pending` також не відновлює вже колись оприбуткований/списаний товар.
6. **Складський UX.** Негайна одиночна/пакетна дія, без полиці/OEM/артикула й зайвого confirm. Таблиця: запчастина, автомобіль, залишок, OEM/артикул, власна ціна, дії. `− / +` та коригування використовують існуючий API operations з request_key; списання/коригування мають причину. Незнята резервація захищена сервером. Фізичне розташування показується окремо від кількості. Локація не видалена: у чинній картці є необов'язкові Склад/Стелаж/Полиця/Комірка; старий текст зберігається до явного нового запису. Деталі зберігаються у наявному location без нової схеми адрес. Непідтверджений HTTP-результат зберігає request_key у scoped sessionStorage; повтор/reload не створює другу операцію.
7. **OEM/артикули.** Порядок OEM перед aftermarket збережено. Довготривалі receipts/snapshots і призначення за server art_id залишаються чинними. Перший артикул — попередній вибір, не доказ OEM/VIN; явне призначення та «Додати 1 шт. та призначити» залишилися. Batch не вимагає і не перепризначає aftermarket-номер: це окрема явна дія над збереженою карткою. Існуючі номери не видаляються.
8. **Переклад/типи позицій.** Ручне уточнення → затверджений словник → збережений DeepL → оригінал. Збереження перекладів і старих checklist names не змінено. Оригінальні назви доступні у звичайному пошуку також для старих карток через точну scoped checklist-прив'язку; нові зберігають оригінал у description. Основний план/лічильник містить фізичні типи. Ремкомплекти, витратні матеріали, інструменти й невизначені типи доступні окремим фільтром і не видаляються. Це можливі типи, не підтверджена комплектація донора.

## OEM API: НЕ ПІДТВЕРДЖЕНО

Перевірені локальні контракти — існуючі Plan.Parts aftermarket categories/articles, `pt_id`, `art_id`, article_nr, brand та характеристики. Повний дозволений provider payload зберігає чинний механізм snapshots/receipts; він не замінений.

Спроба відкрити публічний `https://plan.parts/` у цій сесії завершилася **CONNECT 403** до HTTP-відповіді. Повторів і платних викликів не було. Немає нової незалежної перевірки чинних офіційних OEM/OE/cross/analogue endpoints, параметрів чи тарифів. `oem_available=false` і `external_documentation_verified=false` збережено. Автоматичний OEM вимкнений; ручне введення/підтвердження працює. Вільні поля aftermarket characteristics не видаються за OEM-контракт або підтвердження VIN.

## Перевірки та вимірювання

- **17 backend PASS**, додатковий повтор цільового isolation/CSRF тесту PASS. Атомарний відкат після вставок, concurrent/retry/zero stock, різні pt_id з однаковим перекладом, резерви, ручні категорії, read-only preview, stale token, назви/переклад, збереження попередніх модифікацій. Провайдери тільки offline/mocks.
- **25 frontend unit PASS**, включно з синхронізацією таксономії та відсутністю технічних ID у назвах. Production build PASS; існуюче попередження про розмір bundle залишається. Стандартний prebuild hook виконує свої перевірки; повний backend regression не запускався.
- Для 100 нових типів на тій самій локальній PostgreSQL: попередня реалізація **1.9959 с / 1301 SQL / 100 commit**, нова **0.1974 с / 14 SQL / 1 commit** (~10.1× за часом цього запуску). Попередній route викликаний послідовно in-process без HTTP, новий через TestClient HTTP, тобто транспортні витрати не приховані на користь нової реалізації. Це контрольований synthetic sample, не замір Railway чи реального донора.
- Основний browser regression PASS на production build + PostgreSQL, 1440/390px: модифікація перед розбором, inline assignment/OEM/manual name, reload, масовий вибір, відсутність confirm полиці й платних lookup.
- Розширений browser PASS: **96 фізичних типів + 4 окремі service/review**, додано **93** нових до 3 існуючих одним HTTP, повтор додав **0**. Категоризовано **96 локальних тестових карток**, усі кількості/ціни/OEM/артикули при цьому збережені. `+ / − / correction`, commit з втраченою відповіддю → reload → retry без подвійного надходження. 0 uncaught JS errors, 0 browser paid lookup. Скріншоти й JSON — поруч.

### Захист після зміни модифікації

Той самий donor + source pt_id повторно не створює Part навіть після переходу на інший K-Type. Попередня картка зберігає стару compatibility/provenance, quantity та номер. Вона видима у новому списку з попередженням про звірку; новий aftermarket із іншого K-Type не призначається автоматично, платне отримання для такої неприв'язаної картки в UI заблоковане. Кілька старих карток не зливаються й не вибираються довільно: повертається skipped/review. Однозначні ручні назви/виключення попереднього того самого pt_id доступні без read-side запису. Суперечливі старі рішення потребують уточнення, причому виключення не скасовуються приховано. Явне редагування створює рішення поточного контексту, не видаляючи старі. Окремий regression підтвердив 1 Part / 1 receipt після зміни K-Type.

Фінальна візуальна перевірка: усі 6 колонок видимі й вирівняні на desktop; OEM/артикул і quantity stepper видимі на iPhone; довга локація не створює горизонтального overflow. Необов'язкові 4 поля локації перевірено також у mobile-картці. Збереження локації не змінює quantity, reserve, ціни, OEM, артикул чи фізичний статус. Результати в `visual-results.json`.
