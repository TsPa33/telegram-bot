# Автомобілі → Розбір і запчастини: робочий простір

Перевірено 2026-11-10. Гілка `feature/assembly-component-inventory`, базовий SHA `42cda9232ac5f27e7a8309cf0eef3d82b5b2320c`.

## Чому залишався старий екран

Підтверджений кодовий шлях: Vehicles → ManagedDismantling → VirtualDismantling → UnifiedCatalogue → GlobalCatalogueFlow. Останній уже монтував AssemblyTree, але readiness повертав тільки `enabled=ASSEMBLY_INVENTORY_ENABLED`, за замовчуванням false. Компонент повертав null, а GlobalCatalogueFlow рендерив стару таблицю з артикулами й повідомленнями coverage. Попередні browser-тести запускалися лише з flag=true, тому не перевіряли звичайний вимкнений режим.

Фактичний deployed SHA та Variables робочого Railway у межах цього завдання не перевірялися й не змінювалися. Відтворено саме причину в коді, а не заявлено про зміну staging/production.

Тепер readiness окремо повідомляє `workspace_enabled=true` і попередній `enabled` фізичного редактора. Звичайні читання плану/preview, фізична перевірка й надходження доступні через чинні права, без увімкнення Assembly MVP. Attach/detach/confirm/templates/link/return залишаються за Assembly flag. Інваріанти stock/orders діють завжди. За відсутності inventory.view каталожний доступ не розширюється. Помилка завантаження нового workspace показується як помилка, а не непомітно замінюється старою таблицею.

## Інтерфейс

Збережено чинну оболонку, sidebar, topbar, вкладки, кольори й Day/Night. У робочій вкладці:

- Банер «План розбору сформовано» означає збережений план, а не підтверджену повноту каталогу.
- Чотири показники: потенційні позиції; підтверджена фізична наявність (включно з пошкодженими); фактичні незалежні складські позиції; об’єднання неперевірених/відсутніх/пошкоджених/некомплектних/некатегоризованих позицій, що потребують уваги.
- Основна дія «Додати підтверджені на склад», швидкі дії та фільтри.
- Три колонки: динамічні категорії; компактний tree/list з назвою, категорією, кількістю, окремими фізичним і складським станами та діями; inline-картка.
- Вибір назви, статусу, дії або неінтерактивної області рядка відкриває картку. Лічильники не створюють копій індивідуальних вузлів.
- У картці: фото через наявний авторизований Photo API або placeholder; категорія; фізична наявність/пошкодження/відсутність; необов’язкова примітка; окреме надходження. Складні фізичні дії залишаються згорнутими й gated.
- Категорія без підтвердженої прив’язки показується як «Без категорії», без вигадування категоризації. Джерельні записи не переписано.
- OEM/артикули та історичні списки не видалено. Основна робоча таблиця не містить технічних колонок; попередні списки згорнуто окремо.

На 390 px категорії горизонтальні, картка розташована в межах сторінки, управління доступне дотиком/клавіатурою. Рядки глибоко вкладених вузлів адаптуються, не розширюючи сторінку.

## Масове надходження

Мінімальне розширення наявного Assembly API:

- GET `/vehicles/{id}/assemblies/receipt-preview?include_damaged=false` — read-only підсумок, eligible/skipped з конкретною причиною для кожного рядка й token.
- POST `/vehicles/{id}/assemblies`, `action=receipt_bulk`, `request_key`, `token`, `include_damaged`, `confirm_physical=true` — виконання.

Preview не створює Parts/Operations. До eligible входять тільки підтверджені, включені, ще не пов’язані зі складом, не спожиті фізичні позиції. Відсутні та фізично включені компоненти пропускаються. Для Global Catalogue зберігається попередня перевірка модифікації/збереженого плану та `kind=part`; review/equipment/consumable не обходять її. Пошкоджені включаються лише після окремої явної згоди, стан зберігається.

**Один атомарний пакет — до 100 позицій.** Решта явно зазначаються як наступний пакет. Використано існуючі `DismantlingRequest`, Account/Vehicle/Item/Part locks, Dismantling receipt, Part та Operation. Нової черги, складу чи фінансового ledger немає. Preview перевіряється повторно під lock; зміни між preview і виконанням повертають 409. При помилці будь-якої придатної позиції відкочується весь пакет, без часткового списку успіхів. Повтор того самого ключа повертає збережений результат. Паралельна команда з іншим ключем і старим token не створює дублікатів. Fingerprints попередніх команд збережено.

## Тести

Лише окрема локальна PostgreSQL `warehouse_assemblies_ui_test`; browser harness відмовляється працювати поза localhost:55441 / *_test / local. Робочі БД не використовувалися.

```sh
python -m pytest tests/test_dismantling_workspace.py tests/test_assemblies.py tests/test_warehouse.py -k 'not migrations_roundtrip' -q
# 58 PASS, 1 deselected до додавання останніх двох тестів
python -m pytest tests/test_dismantling_workspace.py -q
# фінальний набір: 8 PASS (перетинається з попереднім)
```

Перевірено: фізична наявність, пошкодження/відсутність, планова кількість, незалежне надходження, bulk preview, окрема згода на пошкоджені, idempotency, два конкурентні запити, rollback на другій позиції, пакети 100+5, виключення компонентів, права read-only працівника, workspace/CSRF, відсутність source API під час bulk. Попередній Assembly/складський набір покриває рекурсивний продаж, компонентний продаж, резерви, історію та контрольоване повернення. Історичний downgrade-roundtrip виключений через forward-only міграційну історію, не через новий UI.

Frontend: **40 PASS** (`dismantling-flow-unit`, `bulk-dismantling-unit`, `vehicle-workspace-unit`, `parts-tabs-unit`). TypeScript/Vite build PASS, попередження >500 kB chunk залишається.

Browser Chromium, **1440/390, Day/Night PASS**, фактичний built UI + локальний API/БД:

1. `WAREHOUSE_E2E=1 node tests/assembly-browser.mjs` — 552 синтетичні потенційні позиції, чинні фізичні зв’язки, пошук/категорії/tree/list, кількість, окреме надходження, пошкодження/блокування продажу, продаж вузла за одну ціну, повторне відкриття, без pageerror/overflow. Фізичні fixture-зв’язки створені лише локально; це не заводський BOM.
2. `WAREHOUSE_E2E=1 node tests/dismantling-workspace-browser.mjs` — локально відтворена **структура збереженого partial-плану зі 113 типами** через чинний `unified_catalogue.persist`, включно з некатегоризованими review-записами. Assembly flag=false. Перевірено новий екран замість старої таблиці, підтвердження без залишку, bulk preview/confirmation/receipt, рівно одна нова складська позиція, збереження всіх 113 після reload, відсутність запитів Plan.Parts/артикулів; окремо — відображення помилки 503 без повернення до старої таблиці.

Це **не копія приватної БД й не доказ повноти реального Volvo**. Власний staging не змінено й staging QA не заявляється.

## Межі та готовність

Нових міграцій немає. Production, Railway Variables, робочі DB/MySQL, оплати та реальні складські записи не змінювалися. Assembly flag не ввімкнено в production/staging. Розгортання не виконувалося.

Після окремого погодження deployment потрібне ручне приймання на фактичному автомобілі та перевірка deployed SHA/schema/rights. Неповна категоризація джерела залишається реальною неповнотою; новий UI не виправляє її вигаданими зв’язками. Масове надходження обмежено пакетом 100 і вимагає явної фізичної перевірки. Фінансові повернення й політика собівартості не розширювалися.
