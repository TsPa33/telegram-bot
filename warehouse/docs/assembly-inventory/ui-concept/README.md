# Інтерфейс розбору автомобіля — затверджена концепція

Історичний звіт для 42cda923. Подальше відокремлення workspace від Assembly flag та масове надходження описані в [актуальному звіті](../../dismantling-workspace/README.md).

Дата перевірки: 2026-11-10. Гілка: `feature/assembly-component-inventory`.

## Реалізація

`AssemblyTree` тепер є робочою областю з категоріями ліворуч, деревом або пласким списком по центру та inline-карткою праворуч. На 390 px категорії прокручуються горизонтально, картка розташовується перед деревом; після відкриття вона отримує фокус і прокручується у видиму область. Закриття повертає фокус до назви деталі. Збережено оболонку, вкладки, навігацію й корпоративні Day/Night tokens.

Один bounded запит дерева завантажує існуючі `DismantlingItem` і фактичні `AssemblyMembership`. Категорії, пошук, зміна виду й розгортання працюють локально. Детальний preview і фото завантажуються лише для вибраної позиції. Числа прогресу походять із фактичних записів; кількість потенційних позицій не видається за залишок незалежних товарів. Поточні каталожні статті/OEM не дублюються в основному робочому списку, залишаються доступними в наявних картках/налаштуваннях.

## Стан та склад — різні дії

- «Перевірити наявність» відкриває картку; «Є», «Пошкоджена», «Відсутня» зберігають результат фізичної перевірки та примітку, без створення `Part` чи надходження.
- «Додати на склад» — окрема явна команда через існуючий dismantling receipt/Part/Operation. Потрібне попереднє підтвердження наявності. Повторне надходження тієї самої позиції заборонене.
- Для потенційної кількісної позиції ± змінює лише кількість плану; для вже складського кількісного товару — чинну аудійовану `correction`. Нульовий залишок дозволений; відсутність потенційної деталі задається статусом, а не видаленням позиції плану.
- Для індивідуально облікованого вузла/компонента ± заблоковано. Включений компонент має фізичну кількість у плані, але не окремий доступний залишок.
- «На складі», «У складі вузла», «Продано», «Продано у складі вузла» відображаються окремо від фізичної перевірки.
- Продаж, відокремлення, підтвердження складу, контрольоване майнове повернення та прив’язка старої складської позиції використовують попередні Assembly MVP API. Форма продажу й складні дії згорнуті.

## Мінімальне доповнення backend

У наявну POST-команду `/vehicles/{id}/assemblies` додано `action=inspect`: `item_id`, preview `token`, `presence`, `quantity`, `note`, `request_key`. Використано існуючі `plan_v3.inspection`, стан/condition, JSON-примітку, аудит і `DismantlingRequest`, без нової таблиці або міграції.

Workspace lock, блокування Part/позицій, перевірка preview-token, авторизація, CSRF та ідемпотентність збережені. Редагування перевіряє також резерви/архівування предків і нащадків, продаж та списання. Застарілі команди повертають 409. Новий UI передає preview-token також для надходження: зміна кількості чи перевірки між preview та receipt блокує операцію. Після формування нового каталожного плану дерево перечитується за revision, без зміни автомобіля або дублювання записів. Нові необов’язкові поля не змінюють fingerprint старих команд. Наявність і кількість не оптимістично підмінюються в UI: після успіху читається фактичний результат, при помилці старі значення залишаються.

Фінансова логіка, рекомендовані ціни, OEM, каталог, замовлення та правила продажу складу не переписані. Відсутня за перевіркою позиція не може бути продана/зарезервована через обхід іншою складською формою.

## Перевірки

```sh
python -m pytest tests/test_assemblies.py tests/test_warehouse.py -k 'not migrations_roundtrip' -q
```

Результат: **52 PASS, 1 deselected**. Після остаточного доповнення receipt-token і повторного читання дерева після створення плану — ще **8 PASS / 25 deselected** у цільовому backend-прогоні (`-k 'inspection or template_version'`; набори перетинаються). Виключений історичний downgrade-roundtrip несумісний з чинною forward-only історією міграцій; це не перевірка UI. Тестова БД створена з поточних міграцій. ## Обмеження та впровадження

- Скриншоти й browser-набір використовують явно позначений synthetic donor. Це не підтвердження реального Volvo BOM, повноти каталогу або staging QA.
- Дерево відображає тільки фактичні збережені зв’язки. Ієрархія з макета не створюється автоматично за схожими назвами.
- Фото походять лише з чинного авторизованого Photo API; за відсутності — placeholder. Зображення з макета не записані як фото автомобіля/деталей.
- Масове автоматичне розбирання всіх компонентів не виконується. Відокремлення конкретної деталі лишається явною дією з перевіркою фізичного складу.
- Майнове повернення не є грошовим refund; політика собівартості/повернень залишається в основному RFC.
- `ASSEMBLY_INVENTORY_ENABLED=false` за замовчуванням. Якщо flag вимкнено, попередній Catalogue UI залишається доступним. Без `inventory.view` новий складський UI не підміняє доступний каталожний екран.
- Нових міграцій немає. Railway, робочі БД, production та платні API не використовувалися. Наявна feature-міграція й загальний rollout описані в [архітектурному RFC](../../assembly-inventory-design.md).
- Зміни призначені для review у feature-гілці/Draft PR №487; увімкнення та staging-приймання потребують окремого погодження.
