# Universal Dismantling v3 — Stage 2A

Локальний наступний етап після `43b766719806134b94b990eb3ea22593eb4ecc10`. Усі зміни — `/warehouse`. Жодного push/deployment/staging apply чи роботи з основним Telegram-ботом.

## Архітектура

`POST /api/v1/vehicles/{id}/dismantling-preview` — stateless read-only endpoint. Використовує існуючі канонічні типи, установчі позиції, варіанти, immutable mappings і fitment evidence. Нових таблиць/міграцій немає, Alembic-head лишається `76af12de4b90`. Модуль `services/dismantling_preview.py` не виконує insert/update/delete/commit, не ставить jobs у чергу і не звертається до старого генератора.

Три джерела:

1. Базові 33 установчі позиції з наявного конструктивного довідника. Працюють і до першої canonical publication — без створення довідникових рядків у БД.
2. Перевірені глобальні типи та варіанти джерельної моделі зі Stage 1–1.5. Кожне оголошення не стає окремою деталлю. Ключ рядка — існуючий placement UUID; OEM/модифікації окремі у variants.
3. Додаткові глобальні варіанти, для яких owner раніше створив явний fitment до марки/моделі цього автомобіля. Невідомий рік/двигун/опція не приховує такого кандидата: він залишається unknown/possible, доки доказ не охоплює конфігурацію.

Власні v1/local джерела читаються тільки з поточного workspace. Дані інших workspace не потрапляють у preview. Сортування category/subcategory/name/placement та variant ID стабільне; у кількості пропозицій і цінових спостереженнях немає подвоєння через кілька шляхів категорій. `quantity:null`: кількість оголошень не визначає конструктивно потрібну кількість деталей.

API повертає `canonical_part_type_id`, `installation_position`, category/subcategory, variants із власними статусами, source/provenance, explanation, compatible_evidence IDs і evidence_details, relevant_offer_count, reference_prices, а також snapshot/rule versions. Непідтверджені та incompatible варіанти залишаються видимими. Установчі позиції і кількість глобальних типів рахуються окремо (`total`, `unique_type_count`); `type_status_counts` означає найвищу доступну оцінку серед позицій типу, а не підтвердження всіх його варіантів.

## Конфігурація і доступ

Тіло запиту: існуючий `ConfigurationPreview` контракт — `facts` і необов’язковий `selected`. Endpoint читає Vehicle та останню актуальну reviewed VehicleConfiguration. Відсутність engine_code, drive, body_type чи options залишається невідомою; маркетинговий T5 не стає точним кодом. Застаріла збережена конфігурація не використовується як підтверджена.

Уточнення для preview — ephemeral; не зберігаються навіть як configuration preview. Сервер примусово понижує їх confidence до reported, тому підміна `confidence:verified` не може створити confirmed. Підтверджені раніше поля зберігають provenance, але конфігурація з пробними уточненнями не вважається reviewed для fitment confirmation. Конфліктні факти дозволяють сформувати список зі статусом unknown, а не виключають позиції.

Права endpoint: **vehicles.view + catalog.view**, сесійна авторизація і CSRF. `vehicles.edit` не потрібен; platform-owner потрібен лише для існуючих адміністративних операцій нормалізації/fitment. Додавати або змінювати owner allowlist не потрібно.

## Правила застосовності

Версія `carpot.dismantling.preview.2a.1`, кожне правило має id/source/version/explanation в API:

- constructive-function: функція з перевіреного словника — кандидат, не підтвердження встановлення;
- powertrain-constraints: наявні B-обмеження для бензин/дизель/HEV/PHEV/BEV; підтверджений BEV може позначати ICE-генератор incompatible, але не видаляє його;
- source-constraints: явні вихідні ознаки пального, приводу та опцій відокремлені від фактів автомобіля;
- missing-or-conflicting: групи A/B/C/D/E, missing/unverified/conflict не перетворюються на «немає»;
- explicit-fitment: confirmed вимагає reviewed конфігурації, verified відомих фактів та явного несуперечливого owner-доказу, що охоплює відомі критерії. Марка/модель, паливо, категорія або оголошення самі не підтверджують сумісність.

Існуючий owner FitmentInput доповнено engine_code/powertrain/drive/body_type/options у JSON-критеріях; це не потребує міграції. Для unknown критеріїв немає позитивного підтвердження. Позитивне твердження для одного року не доводить несумісність для всіх інших.

Не створено вигаданих fitment для свічок/повного приводу/електромотора/панорами. Наявність бензину або AWD не підтверджує конкретну конструкцію. Такі додаткові типи використовуються, коли власник реально визначив глобальну функцію та підтвердив застосовність. Регресійний приклад панорамного даху перевіряє саме цей шлях: unknown опція → видимий unknown кандидат, verified опція + reviewed точний fitment → confirmed.

## VIN-ready

`services/vin_adapter.py`: Protocol `VinAdapter`, строгий `DecodeResult`, локальний `OfflineVinAdapter`. 17 символів, латиниця/цифри без I/O/Q; регістр нормалізується. Це перевірка формату, не автентичності VIN чи OEM-комплектації. Географічно необов’язковий check digit не нав’язується всім VIN.

Адаптер не робить lookup, мережевих запитів або платних інтеграцій і не вигадує WMI/рік/опції. Повертає порожні reported факти; часткова відповідь mock-adapter перевіряється контрактними тестами. Подальший шлях: decoder reported facts → окремий ручний/document review конфігурації Stage 1.5 → read-only preview. Повний build-sheet і припущення не змішуються. У UI можна ввести VIN і відсутні параметри лише для пробного preview; автоматичного декодування немає.

## Ціни

`carpot.comparable-prices.1`: виключно «Ринковий орієнтир», жодних змін selling_price. Показується окремо для **того самого variant ID/OEM/модифікації + явно однакового стану і косметичних ознак + валюти**, мінімум 3 різні пропозиції. Невідомий OEM чи стан — недостатні дані. Кілька observation/path одного offer не збільшують вибірку.

Для кожного offer береться останнє спостереження в межах 90 днів до UTC-часу запиту; майбутні, нульові/відсутні ціни не включаються. UAH і USD не змішуються, FX-конвертації немає. Повертаються мінімум/максимум/медіана, кількість offer та дата. Ціни incompatible варіантів не показуються як орієнтир. В усіх інших випадках — «Ціну не визначено». Це не рекомендована продажна ціна і не обіцянка оцінки авто. Цінові когорти цього етапу читають Global Catalogue v2; власні v1/local джерела залишаються видимими без автоматичного цінового орієнтира.

## UI і побічні ефекти

Окремий блок «Попередній план розбору v3» в деталях автомобіля: поточні значення, пробні уточнення, явна кнопка генерації, категорії/позиції, статуси, причини, джерела, докази, пропозиції та окремі цінові когорти. Дубльований синхронний click блокується ref + busy. При зміні параметрів попередній результат прибирається. Помилка показує конкретну відповідь API і зберігає введення. Reload не повторює preview і не зберігає результат у БД.

Browser-тест виявив автоматичний POST `/dismantling/prepare` старого компонента під час відкриття картки. Тепер старий робочий план монтується **тільки після явної кнопки «Відкрити робочий план розбору»**. Його наявний workflow збережено. Відкриття нового preview не створює історичного плану опосередковано через сусідній компонент.

Низьке покриття не дає підстав для повного автоматичного плану чи автоматичного виключення нерозпізнаних пропозицій.

## Stage 2B

1. Окремий user-confirmed save endpoint для індивідуального нового плану з preview token/configuration+catalogue SHA і idempotency key; перевіряти stale preview.
2. Зберігати вибрані позиції/варіанти, unknown та явні причини виключення як новий план/ревізію. Не переписувати старі DismantlingItem або виключення; зіставляти legacy посилання явно.
3. Додати review та restore для виключень, невідомих конфігурацій і суперечливих fitment. Ніколи не трактувати відсутній рядок як відмову від деталі.
4. Підтвердження розбору і створення залишків — окремі явні транзакції чинного workflow, з повторною перевіркою прав/сесії/версій. Ціни оголошень не стають selling_price.
5. До широкого використання: окремо авторизований тест на B, розширення перевіреної нормалізації/технічних доказів та профілювання великих планів. Stage 2A дозволяє read-only огляд, а не автоматичне підтвердження повного комплекту автомобіля.
