Мета / Definition of Done
Власник хоче робочий наскрізний сценарій, а НЕ нову архітектуру:
ввести VIN → система визначає авто й просить уточнити тільки невідоме → натиснути «Розібрати» → отримати максимальний обґрунтований каталог для конкретної модифікації → вибрати всі/категорію → додати до складу швидко, ідемпотентно, з подальшим редагуванням/продажем.
VIN, розбір, склад і частина каталогізації вже реалізовані в різних модулях.
Не оцінювати як greenfield, не переписувати працюючі підсистеми.

Розібрати
→ handler/endpoint/service → plan generation → canonical 216 fallback → published PRD matching by exact identity → Plan.Parts API. Чи є функції, приховані за feature flag, route guard, owner role, config, disabled frontend control або не зв'язані між собою?
Matching
: чи може runtime використовувати 2 184 raw PRD? Якщо ні — покажи фактичний gate (reviewed source SHA, publication, exact model match), мінімальний шлях до робочого pilot і fallback коли даних немає. Не робити source links доказом повної заводської BOM.
Stock
: select-all, category batch, progress, endpoints, DB transactions, dedupe, collision on retries, qty, article assignment, photos, price, locations, reservations, sales/archive/history protection. Виявити API, що вже існують, але не викликаються UI.
Operations
: staging API/Web SHA, services & env, Alembic versions, migrations, owner roles, CORS, CSRF, auth, background jobs, flags, payment/tokens. Без читання чи друку значень секретів.
Proof
: статичний код-аудит + наявні tests/build, тести без мережі/платних API. Якщо staging недоступний — позначити
NOT VERIFIED
, не вигадувати PASS. Тести не повинні змінювати production/source DB.

Безпека і межі
Перший прохід — read-only аудит.
Не робити деплой, міграції, SOURCE_* DDL, записи Railway чи виклики платних API. Не торкатися production, не видаляти/перепризначати складські позиції. Якщо потрібно щось змінити — спочатку сформувати точний мінімальний план по діючих функціях. Не створювати штучних нових функцій, UI redesign чи фейкову кількість «деталей».
Ціль власника:
не затягувати через повторну реалізацію готового; у першій черзі відновити робочий механізм розбору та stock, UI після цього.
