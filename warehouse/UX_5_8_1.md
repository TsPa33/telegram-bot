## Inventory charts

Native HTML horizontal bar charts avoid a chart-library dependency, keep visible
text values and use keyboard-focusable buttons with pressed selection. Tooltip
uses the real value (native title); selected-value text works with keyboard/touch.
Long lists scroll, empty states are explicit, layouts adapt to all three viewports.

- Categories: actual nonarchived stock quantities, not potential catalog entries.
- Condition: physical condition quantities, not sale/availability state.
- Stock: quantity minus reserved units versus reserved units, matching inventory.
- Vehicle valuation: additive dashboard.vehicle_valuation_by_currency groups exact
  SQL quantity * current selling_price per donor and currency. Missing prices are
  unvalued. UAH and USD are never combined. Old by_vehicle stays UAH for compatibility.
  This is estimated current inventory value, never sales proceeds or profit.

Backend redaction removes both valuation fields without analytics.financial;
frontend Permit also hides them. Chart proportions may use approximate JS Numbers,
but displayed monetary values retain original Decimal strings via money().

## Authoritative sales contract

GET /api/v1/sales/summary

Required permissions (all server-side): analytics.view, analytics.financial,
sales.view, sales.view_financials. UI uses the same combined gate. Authenticated
users missing any permission get 403, rather than a partly redacted financial series.

Parameters:
- date_from/date_to: required ISO calendar dates, inclusive, 1900–2100,
  from <= to, maximum 366 days inclusive.
- interval: day (default), week (Monday), month (first calendar day).
- tz: Europe/Kyiv (default) or UTC.

One parameterized SQL aggregation uses only committed immutable operations with
account_id=current workspace and type=sale. Sale date is Operation.created_at,
not order creation/reservation/shipping/payment date. Kyiv midnight boundaries are
converted with zoneinfo and PostgreSQL grouping uses that same timezone; DST days
may be 23/25 hours. The end bound is exclusive midnight AFTER date_to. First/last
week/month buckets may be partial. Zero-filled periods describe absence of matching
operations, not synthetic sale events. All response totals derive from one SQL
statement/snapshot. Response size is bounded by the requested date window.

Money is taken from Operation.after.sale, validated as recorded unit_price * sold
units = total with currency UAH/USD. Historical order operations lacking that
snapshot use the immutable sale_confirmed event line with the EXACT operation ID,
joined through same-workspace OrderLine. A lateral LIMIT 1 prevents join/event
multiplication. Never use mutable Part prices, mutable order prices or forecasts.
Malformed/missing historical financial metadata contributes only unpriced units/counts.
The quantity is the positive before.quantity - after.quantity for that sale operation.

Response: periods[{date, units, sales_count, unpriced_units, unpriced_sales,
by_currency[{currency,amount,units,sales_count}]}], totals_by_currency, units,
sales_count, unpriced_units, date/timezone semantics, returns_supported=false.
Amounts are Decimal strings with two decimal places; currencies remain separate.
Repeated request keys return the original operation and do not create new ledger
rows, so a replay cannot inflate the series. Reserving/cancelling/creating orders
is not a sale; only actually posted sale operations count. Both quick sales and
order sales use this same ledger, including order reserve consumption.

The projection has a transaction-local 5-second SQL statement timeout. A timed-out
query returns a safe 503 and suggests a shorter period; it does not change business
data. No new index, migration, extension, background job or paid API is introduced.
No claim of tested performance on huge production ledgers is made here.

## Explicit financial limitations

There is no financial sale reversal/refund API in the current model. Sold orders
cannot be cancelled using the ordinary cancellation action. Receipts, corrections,
writeoffs and reserve releases are NOT inferred to be refunds. Therefore the graph
shows posted gross sale amounts, not net sales after returns, cash receipts, payments,
VAT/accounting revenue or profit. A future reversal feature must add an explicit
immutable financial event linked to the original operation, with audit and tests;
it must not silently adjust this graph using inventory corrections/current prices.

The old GET /sales remains compatible. Integration tests compare new aggregates
with actual ledger projection and exercise historical order-event fallback. No
second financial ledger or new sale mutation is created by analytics.

## Frontend

Statistics adds Sales dynamics with day/week/month grouping, date range, 7/30/90-day
presets, Kyiv/UTC selection, per-currency amount bars and total sold-unit bars.
Newer buckets are shown first, so recent sales are visible without scrolling past
all zero-valued old dates. All periods remain available in bounded scrollable lists.
Shown active range is separate from unapplied draft dates. Values/units, unpriced
legacy notice, loading, error/retry and empty state are explicit. useLoad ignores
obsolete responses; old results are hidden during new loading/error. No full sales
ledger is fetched into the browser and no browser-side financial aggregation occurs.
