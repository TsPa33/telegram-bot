## Audit findings and design

- `Part.quantity - reserved_quantity` is available stock. Row/account locks and
  database constraints protect it; damaged condition does not block a real sale.
- Existing stock `sale` recorded quantity change and a Part snapshot, NOT actual
  agreed sale price. Part.selling_price is mutable, never evidence of proceeds.
- Orders already hold fixed `OrderLine.unit_price/currency/line_total`, link
  `sale_operation_id` to the same stock Operation, and append `sale_confirmed`
  event snapshots. Shipping/completion alone must not be counted as a new sale.
- Existing Operation is protected by an append-only database trigger. No edits
  to historical operations or inferred historical amounts are introduced.
- Actor is the authenticated Account in the current one-account identity model;
  there is no separate employee/roles system. Quick sale has no buyer unless
  an order was created. We do not invent either datum.
- Existing internal_notes is one editable text field with before/after audit,
  not a threaded multi-author notes journal. Condition, availability, quantities
  and archived flag remain separate concepts with their existing values.
- No safe reversal/return contract exists. Sale cancellation is deliberately
  unavailable. A future compensating, idempotent audited reversal must link the
  original operation, guard quantities/reservations, prevent repeated reversal,
  preserve commercial currency/amount and coordinate order return state. Never
  edit/delete a sale or use a manual receipt as an equivalent financial reversal.

## Backend additions — no migration

`StockInput` accepts optional `sale_price` (Decimal, >=0, <=2 decimals) and
`sale_currency` (UAH/USD), together and for sale only. Existing quantity-only
clients remain valid. HTTP financial sales require the existing UUID request_key.
New financial fields are included in the replay fingerprint; absent fields are
excluded to preserve the EXACT old fingerprint shape, including existing pending
stock requests. A changed amount with a reused key returns 409.

`Operation.after.sale` version 1 records actual unit_price, currency, total,
quantity, source, actor name and donor snapshot, created before the immutable
operation INSERT. Monetary JSON values are decimal strings. Part list price is
NOT overwritten. New order sales enrich the SAME operation with order/buyer
snapshot and actual agreed line price. No second ledger or stock decrement.

Authenticated endpoints (existing CSRF/Origin checks for writes):
- `PATCH /api/v1/parts/{id}/notes`: internal_notes + expected_notes; lock and
  compare-and-set, 409 on conflicting edit. Audit records before/after.
- `PATCH /api/v1/parts/{id}/inspection`: optional condition/availability; audited,
  locks active tenant-owned Part, never changes quantity or reservation.
- `GET /api/v1/sales`: existing sale Operations only, bounded offset/limit50
  (max100), q name/OEM/article, vehicle_id, source quick/order, date_from/date_to.
  One response row per actual stock sale operation. Archived/zero-stock parts
  remain represented. Price unknown for legacy quick sales; old order prices
  come from existing sale_confirmed event linked to that exact sale operation.
  Old donor labels without a commercial snapshot are explicitly marked current.
- `GET /api/v1/workshop/readiness`: separate contract7, expected schema head still
  d86f21a90b34. Existing sales-workspace contract5 and orders contract6 unchanged.

No new tables, migration, backfill or changes to existing stored amounts.
The schema head remains d86f21a90b34. Existing migration preservation tests run.

## Frontend

Both stock modes and quick search share SalesWorkspace operations. Detail main
buttons: Sell, Note, Price, Order. Edit/history/inspection/archive under More;
stock transfer/writeoff/quantity correction under collapsed advanced operations.
Legacy operational screens remain available from Settings and clearly state
that these are available to all account users, NOT role-protected admin access.
Reservations for customers remain in Orders. Old quantity-only forms explicitly
explain they do not capture financial sale prices.

Quick sale confirms quantity, actual unit price/currency and optional note.
Unresolved request body/key stays in sessionStorage and input is locked for exact
retry. Double-submit uses a synchronous ref guard. Network/unknown failures never
clear it; a reloaded last-unit sale can replay even when current available=0.
No optimistic stock mutation. Reload after confirmed backend write. 409/422
rejects clear an unsuccessful request; price changes use the existing price API.

Sales page shows actual price or explicit unknown, quantities, time, source,
buyer/actor when recorded and note; no mixed-currency totals or invented revenue.
Notes CAS protects the quick note path; legacy full-card PUT has no generic
optimistic concurrency and remains a limitation. Full browser refresh reloads a
conflicted note before trying a deliberate merged edit.

Part graphics resource stage: empty reviewed registry and pure category/type
resolver for engine, transmission, door, headlight, bumper, wheel, suspension,
electronics and unknown. Only exact generic labels are classified; no fitment or
OEM claims. Until licensed/owned artwork is supplied, normal part text remains
the fallback. No image API, decorative placeholder icons or stock-image copying.
