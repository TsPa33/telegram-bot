# Plan.Parts: окремий чекліст потенційних деталей

## Поведінка

Марка → модель → рік → явний вибір модифікації → збережений K-Type вже реалізовані.
У картці збереженого автомобіля натисніть **Завантажити чекліст за K-Type**.
Backend викликає лише `GET https://cdn.plan.parts/api/v1/aftermarket/catalog/categories?ktype=...`
із Bearer-ключем backend. Контракт перевірено на наданому JSON: success/data/results,
data.ktype, data.count, 632 записи з pt_id/name/article_count. Живих запитів під час
розробки/тестів немає. Інші каталоги, OEM, аналоги й catalog_url не завантажуються.

Створюється окремий запис на pt_id, навіть якщо назви збігаються. Статус — unchecked.
Це можливі типи деталей, а не підтверджена комплектація. Таблиці parts, categories,
залишки та резерви не змінюються. article_count — кількість каталожних артикулів,
ніколи не складська кількість. Ієрархію й українські назви API не надає: їх не
вигадуємо. Українська назва редагується вручну, англійська зберігається окремо.

Збережені результати належать конкретному акаунту та автомобілю; спільного кешу
чи масового імпорту немає. Звичайне читання й повторне завантаження збереженого
K-Type не викликають провайдера, включно з порожньою відповіддю. **Оновити з
Plan.Parts** — окрема підтверджена дія, що може витратити токени. Статуси, переклади,
примітки та відсутні в новій відповіді записи зберігаються. Після зміни K-Type
старий список доступний лише для читання через прапорець попередніх K-Type.
Архівовані авто доступні лише для читання.

Ліцензійні права на збереження/повторне використання не підтверджені. До їх перевірки
залишити PLAN_PARTS_ENABLED=false. API-ключ не передається у frontend. Не вмикати
живий тест без окремого погодження витрат.

## Внутрішній API

- GET `/api/v1/vehicles/{id}/plan-parts-checklist?limit=50&offset=0&include_history=false`:
  збережені записи, пагінація, поточний K-Type та historical_total; жодного paid call.
- POST той самий шлях: один import за збереженим K-Type, або reuse.
  `?refresh=true` — явне повторне звернення; K-Type від клієнта не приймається.
- PATCH `/api/v1/vehicles/{id}/plan-parts-checklist/{item_id}`: лише status
  (unchecked/present/absent/damaged), name_uk, notes. Невідомі поля відхиляються.

Потрібна поточна Warehouse-сесія; POST/PATCH також CSRF. Перевірка account_id
перед зовнішнім запитом; composite FK додатково унеможливлює чужий account_id.
Імпорт/редагування аудіюються. Блокування рядка авто серіалізує імпорти й зміну
K-Type. Чинні обмеження Plan.Parts: 10 запитів/акаунт/хв, 60/процес/хв та 60 с
між однаковими запитами; timeout, перевірка TLS/розміру/структури відповіді, без
автоповторів. Ліміти процесу не є глобальним бюджетом кількох реплік: залишити
одну staging-репліку; для масштабування потрібен спільний ліміт.

## Міграція та staging — тільки після погодження

Нова ревізія `a84d2c19e705`, після `c91e72b6a410`: окрема таблиця
vehicle_checklist_items, nullable vehicles.checklist_ktype/checklist_synced_at,
складений unique/FK для ізоляції. Наявні автомобілі, ktype=NULL, склад і аудит
зберігаються. Жодного backfill або зовнішнього запиту в міграції.

1. Зробити й перевірити резервну копію окремої Warehouse staging БД за BACKUP_STAGING.md.
2. Погодити Warehouse API/web release з feature-гілки; production не чіпати.
3. Чинний staging entrypoint під advisory lock застосує upgrade head перед запуском API.
   Не підміняти його прямим uvicorn і не запускати паралельну pre-deploy міграцію.
4. У Warehouse API: `python -m alembic current`, `python -m alembic heads`,
   `python -m alembic check`. Очікуваний head: b72f03d8e196 (наступна nullable-date ревізія; QUICK_VEHICLES.md), без schema drift.
5. HTTPS `/health` → 200. Перевірити login, ручне створення, старі авто й залишки
   при вимкненому провайдері. Після погодження ліцензії/токенів перевірити один
   явний import, unchecked, переклад/статус, повторне відкриття та незмінний склад.
6. При помилці міграції не розгортати новий web, перевірити фактичну ревізію та логи;
   виправити причину. При успішній міграції й помилці API перевага forward fix.
   Старий образ може вважати нову ревізію unhealthy. Downgrade до c91e72b6a410
   видаляє весь новий чекліст і переклади: лише після backup та окремого погодження.
   Відновлення спочатку в окрему тестову БД, ніколи поверх production.

## Локальна перевірка

Backend: у warehouse/backend задати WAREHOUSE_TEST_DATABASE_URL для окремої
локальної PostgreSQL з назвою, що закінчується `_test`, і запустити
`../.venv/bin/python -m pytest tests unit_tests -q`. Тести очищають тільки цю БД.
Перевіряються реальні JSON-фікстури, повторний/паралельний import, account/CSRF,
ліміти й некоректні відповіді, збереження ручних змін, міграція зі старими даними
та Alembic schema check. Провайдер замінений httpx.MockTransport.

Frontend у warehouse/frontend: `npm run build`, `node tests/plan-parts.mjs`,
`node tests/plan-parts-checklist.mjs`. Chromium (/usr/bin/chromium) перевіряє
production assets у desktop та iPhone viewport з підставним backend; реальний
Safari та наскрізний staging-тест ще потребують ручної перевірки після погодження.
